Slide 1 Title

Hi everyone, my name is Paul Semaan and this is my final project for CECS 429. The project is called GutenSearch. It is a working mini search engine over a small corpus of classic literature, and I built it to demonstrate the IR techniques we covered in class as one complete pipeline.

Slide 2 Motivation

The reason I picked this project is honestly that everything we covered this semester tends to live as a separate formula on a separate slide. Tokenization. Inverted indexes. tf-idf. BM25. K-grams. Spelling correction. You learn each of these in isolation, but you only really see how they connect when you put them in the same system. I wanted a working artifact I could actually type queries into, see results from, and reason about, not a pile of disconnected algorithms.

Slide 3 Problem Statement

The goal was to build a complete mini search engine, end to end. It needed to index a real natural language corpus, support all four query types from class, which are Boolean, phrase, wildcard, and ranked, offer two different ranking algorithms for comparison, do spelling correction on misspelled queries, and ship as a deployable static website with no backend, no database, and no server.

Slide 4 Dataset

For the corpus I picked ten public domain novels from Project Gutenberg, around 760,000 tokens total. They span genres and eras, from gothic horror to detective fiction to social satire to science fiction to children's literature. I picked these because they are linguistically rich, freely redistributable, and familiar enough that you can sanity check the search results just by thinking about the books. The build script downloads them directly from gutenberg.org and caches them locally, so the corpus is fully reproducible.

Slide 5 Architecture

The system is split into two halves. The offline half is a single Python script that tokenizes the corpus, builds the inverted index and the k-gram index, computes all the document statistics, and writes everything out as JSON. The online half is a static web page that loads that JSON and runs every search query directly in the browser. There is no backend. This means the whole system deploys to GitHub Pages with one click, which also gets me the bonus five points for a live demo URL.

Slide 6 Indexing

Tokenization is intentionally simple. Lowercase, alphabetic characters only, no stemming, and stopwords stay in the index. The reason stopwords stay is that phrase queries depend on every original position being present. The inverted index is positional, so for each unique term I keep a list of which documents it appears in and at which token offsets. Positions are delta encoded to shrink the JSON by about 40 percent. The k-gram index is built over 3-grams of every vocabulary term, with sentinel characters at the start and end of each term to make prefix and suffix wildcards work properly.

Slide 7 Query Evaluation

The system supports four query types and auto detects which one to use from the query string. Boolean queries use a small shunting yard parser that converts to reverse Polish notation, then I evaluate by walking the RPN expression and doing set intersect, union, or difference. Phrase queries intersect the document sets of every term and then for each candidate document walk the position list of the first term and check if each subsequent term appears at the next consecutive offset. Wildcard queries intersect the k-gram lists of the definite trigrams and then filter the results with a regex to drop false positives. Ranked queries use either tf-idf cosine or BM25, returning the top K with scores. And spelling correction is Damerau-Levenshtein over candidates that pass a 3-gram Jaccard similarity threshold of 0.3.

Slide 8 Ranking

Here are the two ranking modes. The first is tf-idf cosine using the lnc dot ltc scheme from the Manning textbook. For each query term it multiplies a log scaled query term frequency by an idf weight, multiplies a log scaled document term frequency, and divides by the L2 norm of the query and the document vectors, which gives you cosine similarity. The second is BM25 with k1 equal to 1.5 and b equal to 0.75. BM25 differs from tf-idf cosine mainly in that it saturates term frequency through the k1 parameter and accounts for document length explicitly. Both rankers are exposed in the UI as a dropdown, so you can switch between them at query time.

Slide 9 Results, Index

Here are the index statistics on the actual corpus. Ten documents, around 760,000 tokens, about 33,000 unique terms, about 14,000 unique 3-grams. The complete JSON index is about 30 megabytes, dominated by the positional postings, and it loads into the browser in well under a second on a typical laptop. The corpus raw text takes another 4.5 megabytes which the frontend fetches lazily for snippet generation.

Slide 10 Results, Latency

These are the per-query latency numbers I measured in Chrome on a development laptop. Boolean queries are the fastest, around 3 milliseconds, because they are just set operations on small posting lists. Wildcards are also fast, about 4 milliseconds, since k-gram filtering is very effective. Phrase and ranked queries are in the high single digits to low double digits. The slowest is spelling correction at around 35 milliseconds, which makes sense because it computes edit distance against several hundred candidates after k-gram filtering. Everything else is essentially instantaneous from the user point of view.

Slide 11 Results, Ranking Sanity

To sanity check the ranking quality I ran some queries where the right answer is obvious. Vampire blood transylvania returns Dracula at the top. Mr Darcy returns Pride and Prejudice. Scrooge Christmas returns A Christmas Carol. Rabbit hole returns Alice in Wonderland. Holmes Baker Street returns Sherlock Holmes. Martians invasion returns War of the Worlds. Both tf-idf cosine and BM25 agree on every sanity check query. BM25 tends to spread scores more aggressively, so the gap between the top result and the second one is larger under BM25, but the ordering is the same.

Slide 12 Conclusion and Future Work

What worked is the main point of the project. Every IR concept from the course is implemented in one working, deployable system. The whole thing is a few hundred lines of Python plus a few hundred lines of JavaScript. As for future work, the most useful next steps would be Porter stemming to handle morphological variation, query expansion through synonyms or pseudo relevance feedback for better recall, a sharded index to scale beyond ten documents, learning to rank using labeled relevance judgments, and a real noisy channel spelling model trained on actual misspellings rather than the flat edit distance ranker I have now.

Slide 13 Target Venue

Target venue for this project is the SIGIR Demonstrations Track. SIGIR is the top venue for information retrieval research, with the highest h5 index under IR in Google Scholar Metrics in 2024. They have a dedicated Demonstrations track for working systems, which is exactly what GutenSearch is. The system implements the classical IR techniques that SIGIR has been publishing on for decades, and the static deploy makes the demo trivial for reviewers and attendees to use in the browser. I think the system is a natural fit for that venue.
