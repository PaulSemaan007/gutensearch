GutenSearch

A Mini Search Engine over Classic Literature

Paul Semaan   CECS 429   Professor Xin Qin   Spring 2026

Abstract

Abstract. GutenSearch is a working mini search engine built over ten classic public domain novels from Project Gutenberg. The system implements the full stack of techniques covered in CECS 429 in one running pipeline. That includes tokenization, a positional inverted index, a 3-gram index for wildcard queries, Boolean and phrase queries, ranked retrieval using both tf-idf cosine and BM25, and Damerau-Levenshtein spelling correction. The build side is a single Python script that turns raw books into a JSON index. The search side is a static web page that runs every query directly in the browser, with no backend. On a corpus of 778,201 tokens across 22,794 unique terms, the index serializes to 5.9 MB and most queries return in under 15 milliseconds.

1. Introduction

Everything we covered in CECS 429 tends to live as a separate formula on a separate slide. Tokenization is one lecture. Inverted indexes is another. tf-idf is a third. BM25, k-grams, and spelling correction are each introduced on their own. You only really see how they fit together when you put them in the same system, and that is what this project does. I wanted a working artifact I could type queries into, not just a stack of disconnected algorithms.

The corpus is ten well known public domain novels from Project Gutenberg. They were chosen because the books are linguistically rich, freely redistributable, large enough that ranking has something interesting to do, and familiar enough that you can sanity check the results just by thinking about the books. A query for the words vampire blood transylvania ought to put Dracula at the top. A phrase query for mr darcy should match exactly one book.

The main contribution is that GutenSearch is a complete IR pipeline from raw Project Gutenberg files to ranked search results, end to end, with no external dependencies on either side. The build runs on the Python standard library alone. The search runs in any browser. The system is deployed live at paulsemaan007.github.io/gutensearch.

2. Related Work

The methods used here are textbook IR, and the canonical reference is the Manning, Raghavan, and Schütze textbook, Introduction to Information Retrieval [1]. The tf-idf scoring scheme, cosine similarity ranking, SMART notation, positional postings model, k-gram index for wildcards, and Damerau-Levenshtein spelling correction all come from that book.

The BM25 ranking function in this project is the version derived by Robertson and Zaragoza [2], which gives the standard parameter defaults, k1 around 1.5 and b around 0.75, that are still considered reasonable today. BM25 differs from tf-idf cosine in two ways that matter for a mixed corpus. It saturates term frequency through the k1 parameter, and it normalizes by document length explicitly. The length normalization matters here because the books range from around 27,000 tokens for Alice in Wonderland up to 163,000 tokens for Dracula, roughly a six to one ratio.

For a production comparison, Apache Lucene [3] is the canonical open source search engine, used inside both Elasticsearch and Solr. Its architecture matches the general shape of GutenSearch, just at much larger scale and with more sophisticated index encoding such as variable byte and PFOR compression. GutenSearch can be thought of as a minimal in browser analog of one Lucene segment with a small corpus.

The spelling correction component draws on the noisy channel formulation of Kernighan, Church, and Gale [4], although the probability model here is simplified down to a direct edit distance ranking with document frequency as the tie breaker. The k-gram pre-filter comes from the original work of Angell, Freund, and Willett [5] on trigram overlap for approximate string matching.

3.2 System Architecture

The system is split into two halves. The build side is a single Python script, build_index.py, that downloads the corpus, tokenizes it, builds the inverted and k-gram indexes, and writes everything to JSON. The search side is a static web page made of index.html, style.css, and app.js, which fetches the JSON and runs every query in the browser. The pipeline is shown in Figure 1.

Figure 1. The GutenSearch pipeline. Offline build, online search, no backend.

The advantage of this split is that the system is trivially deployable. Pushing the repository to GitHub and enabling GitHub Pages produces a live demo URL with no configuration. The cost is that the entire index has to be loaded into memory on first query, but for a corpus of this size that takes well under a second on a typical laptop.

3.3 Tokenization and Indexing

Tokenization is intentionally simple. The text is matched against the regular expression for runs of letters and apostrophes, every match is lower-cased, and apostrophes are dropped, so can't becomes cant and O'Brien becomes obrien. I deliberately did not apply a stemmer. A full Porter implementation would have added complexity for a small accuracy gain on this corpus, and a half-baked stemmer would have introduced confusing results. The cost of skipping stemming is that searches for run do not match running, which the user-facing query syntax compensates for with wildcards such as runn-star.

Stopwords are recorded as metadata but kept in the postings, which is necessary for phrase queries to work properly. A phrase like of the dead would break if the words of and the were thrown away. The ranked retrieval algorithms naturally down-weight stopwords through idf anyway.

The positional inverted index maps each unique term to a list of document id and position list pairs. To keep the JSON file size down, position lists use delta encoding. The first position is stored absolutely, and every subsequent one is stored as the difference from the previous. This reduces position storage by roughly 40 percent compared to absolute positions. A single posting looks like this.

term darcy df 1 postings document 1342, at token positions 147, 312, 88, 203, and so on

The 3-gram index supports wildcard queries. Every term is padded with a sentinel dollar sign at both ends, then each trigram of the padded term is mapped to that term. At query time the wildcard pattern is decomposed into its definite trigrams, meaning the ones that contain no asterisk, the candidate vocabulary is the intersection of the term lists for those trigrams, and the candidates are filtered against the actual regex pattern to drop the inevitable false positives.

3.4 Query Evaluation

The system supports four query modes and auto-detects which one to use from the query string. A double-quoted query is treated as a phrase. A query containing an asterisk is treated as a wildcard. A query containing the keywords AND, OR, or NOT is treated as Boolean. Everything else is a free-text ranked query.

Boolean queries go through a small shunting-yard parser that converts to reverse Polish notation, with AND and OR as binary operators. A NOT followed by a term is collapsed into a single negated token at the lexing stage, which avoids the awkwardness of mixing unary and binary operators in the same precedence table. The evaluator walks the RPN expression and performs set intersection, union, or difference against the full document set.

Phrase queries retrieve the positional posting lists for all n terms in the phrase, intersect the document sets, then for each candidate document walk the position list of the first term and binary-search every subsequent term's positions for the consecutive offset. The first match in a document is enough, and the algorithm short-circuits.

Ranked queries use either tf-idf cosine or BM25, selectable in the UI. Both return the top K, configurable in the UI with a default of 10. The scoring formulas are below.

tf-idf cosine, lnc.ltc weighting
score(q, d) = sum over t in q of (1 + log tf_qt) × log(N / df_t) × (1 + log tf_dt), divided by the product of the query norm and the document norm
BM25, with k1 = 1.5 and b = 0.75
score(q, d) = sum over t in q of idf(t) × (k1 + 1) tf_dt, divided by (tf_dt + k1 (1 − b + b × |d| / avgdl))

The idf term for BM25 is computed as log of ((N − df + 0.5) divided by (df + 0.5), plus 1). The lnc document weights are precomputed at build time, so the query-time work is just term lookup, multiplication, and accumulation.

3.5 Spelling Correction

If a ranked query returns no results, the system tries to correct the first non-stopword query term. It takes the trigrams of the misspelled query, finds candidate vocabulary terms whose trigram overlap with the misspelling, measured by Jaccard similarity, is at least 0.3, then scores every surviving candidate by Damerau-Levenshtein edit distance with document frequency as the tie-breaker. The single best candidate is offered in the UI as a suggestion the user can click to re-run.

4.4 Wildcard and Spelling Correction

The wildcard query monst-star expands to the term set monster, monsters, monstrous, and monstrosity, and returns three documents, Frankenstein, Dracula, and The Picture of Dorian Gray. The query star-ation expands to over 200 terms, which exposes a small limitation. Very general wildcard patterns produce too many candidates to display usefully. A real system would either truncate or fall back to ranked retrieval over the wildcard expansion.

For spelling, the correction component handles common misspellings well. The word frankinstien gets corrected to frankenstein, elisabeth to elizabeth, and scroge to scrooge. The correction breaks down for misspellings more than three edits away from any vocabulary term, or for misspellings whose trigram overlap with every candidate falls below the 0.3 Jaccard threshold.

4.5 Limitations

The system has a handful of limitations worth being honest about.

  • No stemming. The word run does not match running in ranked retrieval. Wildcards paper over this.
  • Unranked phrase results. Phrase queries return an unordered set of matching documents rather than a ranked list.
  • Index loaded eagerly. The full index is loaded into memory at startup. For corpora much larger than this, the index would need to be sharded and loaded lazily.
  • Spelling fires only on empty result sets. A real system would also surface did-you-mean hints for queries that return very few results but might be misspelled.
  • Simple snippet generation. Snippets find only the first occurrence of the query term in a document rather than the best occurrence.
  • No proximity or fielded queries. The system does not support proximity operators or queries scoped to just the author or just the title.

5. Conclusion and Future Work

GutenSearch demonstrates that the textbook IR algorithms covered in CECS 429 are enough to build a working, deployable search engine end to end, with no external dependencies on either side. The whole thing is a few hundred lines of Python and a few hundred lines of JavaScript. Pushing it to GitHub Pages produces a live URL with no further configuration.

The most useful next steps, in rough order of impact, would be these. First, adding Porter stemming would close the run and running gap that wildcards currently paper over. Second, query expansion through synonym lookup or pseudo relevance feedback would help recall when the user's vocabulary differs from the author's. Third, the index could be sharded by alphabet range and loaded lazily, which would let the same architecture scale to much larger corpora. Fourth, learning to rank using labeled relevance judgments on a small set of queries could improve ordering beyond what either tf-idf cosine or BM25 produces on their own. Fifth, the spelling correction component could be replaced with a proper noisy-channel model trained on actual misspellings rather than the flat edit-distance ranker.

There is also a natural extension toward indexing the user's own document collection, things like research papers, course notes, or personal email, instead of a fixed corpus. The architecture supports this directly. Replace the corpus list in build_index.py with a directory walk, and everything downstream works unchanged.
