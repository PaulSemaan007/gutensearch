GutenSearch, a mini search engine over classic literature

Abstract

GutenSearch is a working mini search engine I built over ten classic public domain novels from Project Gutenberg. The aim was to take all the IR techniques we covered this semester and put them into one running system. That includes tokenization, a positional inverted index, a 3-gram index for wildcard queries, Boolean and phrase queries, ranked retrieval with both tf-idf cosine and BM25, and spelling correction based on Damerau-Levenshtein edit distance. The build pipeline is a Python script that turns the raw books into a JSON index, and the search side is a static web page that runs every query directly in the browser. There is no backend. On a corpus of around 760,000 tokens the index comes out to about 30 megabytes and most queries return in under 50 milliseconds.

Introduction

I picked this project because everything we covered in CECS 429 tends to live as a separate formula on a separate slide. Tokenization is one lecture. Inverted indexes is another. tf-idf is a third. BM25 and k-grams and spelling correction are introduced on their own. You only really see how they fit together when you put them in the same system, and that is what I wanted to do. I also wanted a working artifact I could actually type into and demo, rather than a stack of algorithms that never get connected.

The corpus I chose is ten well known public domain novels from Project Gutenberg. I picked them because the books are linguistically rich, freely redistributable, large enough that ranking has something interesting to do, and familiar enough that you can sanity check the results just by thinking about the books. A query for vampire blood transylvania ought to put Dracula at the top. A query for "mr darcy" as a phrase ought to match exactly one book.

The main contribution of the project is that it is a complete IR pipeline, from raw Project Gutenberg files all the way to ranked search results, with no external dependencies on either side. The build runs on the Python standard library alone. The search runs in any browser. Pushing the whole thing to GitHub Pages gives you a live demo URL with no further work.

Related Work

The methods used in this project are textbook IR. The clearest reference for them is the Manning, Raghavan, and Schütze textbook called Introduction to Information Retrieval [1], which is the standard book used in IR courses and which formalizes nearly every component I used here. The tf-idf scoring scheme, cosine similarity ranking, SMART notation, positional postings model, k-gram index for wildcards, and Damerau-Levenshtein based spelling correction all come from that book.

The BM25 ranking function I used is the version described by Robertson and Zaragoza [2], which gives the standard derivation and the parameter defaults that are still considered reasonable today, with k1 around 1.5 and b around 0.75. BM25 differs from tf-idf cosine mainly in that it saturates term frequency and explicitly accounts for document length. That matters more than you would think on this corpus, since the books range from around 27,000 tokens (Alice in Wonderland) up to around 163,000 tokens (Dracula).

For a production scale comparison, Apache Lucene [3] is the canonical open source search engine, used inside both Elasticsearch and Solr. Its architecture is the same general shape as GutenSearch, just at a much larger scale and with more sophisticated index encoding. Offline index building, segmented inverted files, BM25 as the default ranker. GutenSearch can be thought of as a minimal in-browser analog of one Lucene segment with a small corpus.

The spelling correction component draws on the noisy channel formulation by Kernighan, Church, and Gale [4], although I simplified the probability model down to a direct edit distance ranking with document frequency as the tie breaker. The k-gram pre-filter I use is from the original work by Angell, Freund, and Willett [5] on trigram overlap for approximate string matching.

Methods

The corpus is ten public domain novels downloaded from Project Gutenberg by the build script. They span genres and eras, from Austen's social satire in 1813 to Wells's science fiction in 1898. The full list with approximate token counts is below.

Total corpus size is roughly 760,000 token occurrences after stripping the Project Gutenberg headers and footers off each file. The raw downloaded files get cached locally so the build does not re-download them on subsequent runs.

Tokenization is deliberately simple. I match the text against the regular expression [A-Za-z']+, lowercase every match, and drop apostrophes, so "can't" becomes "cant" and "O'Brien" becomes "obrien". I deliberately did not apply a stemmer. A full Porter implementation would have added a lot of code for a small accuracy gain on a corpus this size, and a half baked stemmer would have introduced confusing results. The cost of skipping stemming is that searches for "run" do not match "running", so to make up for that, the user can use wildcards like runn* explicitly.

Stopwords are recorded as metadata but they are kept in the postings. That is necessary for phrase queries to work properly. A phrase like "of the dead" would break if "of" and "the" were thrown away during tokenization. The ranked retrieval algorithms naturally down weight stopwords through idf anyway, so they do not need to be removed for relevance either.

The positional inverted index maps each unique term to a list of (document id, position list) pairs. Positions are token offsets within the document. To keep the JSON file size down, position lists use delta encoding. The first position in each list is stored absolutely and every subsequent one is stored as the difference from the previous one. That reduces position storage by roughly 40 percent compared to absolute positions.

The 3-gram index supports wildcard queries. Every term is padded with a sentinel $ at both ends, then every consecutive trigram of the padded term is mapped to that term. At query time the wildcard pattern is split into its definite trigrams, meaning the ones that contain no asterisk, the candidate vocabulary is the intersection of the term lists for those trigrams, and then I filter the candidates with a regular expression to drop the false positives that k-gram intersection always produces.

The system supports four query types and auto detects which one to use from the query string. A double quoted query is treated as a phrase. A query containing an asterisk is treated as a wildcard. A query with the keywords AND, OR, or NOT is treated as Boolean. Anything else is treated as a free text ranked query.

Boolean queries go through a small shunting yard parser that converts the query to reverse Polish notation, with AND and OR as binary operators. NOT followed by a term is collapsed into a single negated token at the lexing stage, which avoids the awkwardness of mixing unary and binary operators in the same precedence table. The evaluator walks the RPN expression and performs set intersection, union, or difference against the full document set.

Phrase queries take the n terms in the phrase, retrieve their positional posting lists, intersect the lists by document id, and then for each candidate document walk the position list of the first term and binary search every subsequent term's positions for the consecutive offset. The first match in a document is enough, the algorithm stops there.

Two ranking schemes are available, selected by a dropdown in the UI. The tf-idf cosine ranker uses the lnc.ltc weighting scheme from the Manning textbook. For each query term it multiplies a log scaled query term frequency by an idf weight, multiplies a log scaled document term frequency, and divides by the product of the query norm and the document norm. The document norm is precomputed during indexing. The BM25 ranker uses the Robertson and Zaragoza formula with k1 = 1.5 and b = 0.75. The main difference between the two is that BM25 saturates term frequency through the k1 parameter and explicitly normalizes by document length, while tf-idf cosine accounts for document length only through the L2 norm in the denominator. Both rankers return the top K documents, where K defaults to 10 and is configurable in the UI.

For spelling correction, if a ranked query returns no results, the system tries to correct the first non stopword query term. The procedure is to take the trigrams of the misspelled query, find candidate vocabulary terms whose trigram overlap with the misspelled query (measured as Jaccard similarity over their trigram sets) is at least 0.3, then score every surviving candidate by Damerau-Levenshtein edit distance with document frequency as the tie breaker. The single best candidate is offered in the UI as a suggestion the user can click to re-run the query.

The system is split into two pieces. The build side is a single Python script called build_index.py that downloads the corpus, tokenizes it, builds the indexes, and writes everything to JSON. It uses the Python standard library only, so the only install step is Python 3.8 or newer. The search side is a static web page (index.html, style.css, app.js) that fetches the JSON index and runs every query directly in the browser. There is no backend. The big advantage of this split is that the system is trivially deployable. Pushing the repo to GitHub and enabling GitHub Pages produces a live demo URL with no configuration. The cost is that the entire index has to be loaded into memory on first query, but for a corpus of this size that takes well under a second on a normal laptop.

Both rankers agree on every query in this sample. BM25 tends to spread scores more aggressively, so the gap between the top result and the second one is wider under BM25, but the ordering is the same.

For wildcards I tried monst*. It expands to the term set monster, monsters, monstrous, monstrosity and returns three documents, Frankenstein, Dracula, and The Picture of Dorian Gray. The query *ation expands to over 200 terms, which exposes a small limitation. Very general wildcard patterns produce too many candidates to display usefully. A real system would either truncate or fall back to ranked retrieval over the wildcard expansion.

For spelling I tried frankinstien, elisabeth, and scroge. Each one gets corrected to frankenstein, elizabeth, and scrooge. The correction breaks down for misspellings that are too far from any vocabulary term, more than three edits, or whose trigram overlap with every candidate is below the 0.3 threshold.

There are a few limitations I want to be honest about. There is no stemming, so run does not match running in ranked retrieval unless the user adds a wildcard. Phrase queries return an unordered set of matching documents rather than a ranked list. The full index is loaded into memory at startup, which would not scale to a corpus much larger than this without sharding. Spelling correction only fires when there are zero results, not when there are very few. Snippet generation picks the first occurrence of the query term in a document rather than the best one. There is no support for proximity queries or fielded queries such as searching only the author or the title.

Conclusion and Future Work

GutenSearch demonstrates that the textbook IR algorithms from CECS 429 are enough to build a working, deployable search engine end to end, with no external dependencies on either the build side or the runtime side. The whole thing is a few hundred lines of Python and a few hundred lines of JavaScript. Pushing it to GitHub Pages gives you a live URL with no further work.

If I kept working on this, the most useful next steps would be these. First, adding Porter stemming would close the run versus running gap that wildcards currently paper over. Second, query expansion through synonym lookup or pseudo relevance feedback would help recall when the user's vocabulary differs from the author's. Third, the index could be sharded by alphabet range and loaded lazily, which would let the same architecture scale to a much larger corpus. Fourth, learning to rank using labeled relevance judgments on a small set of queries could improve ordering beyond what either tf-idf cosine or BM25 produces on their own. Fifth, the spelling correction component could be replaced with a real noisy channel model trained on actual misspellings rather than the flat edit distance ranker I have now.

There is also a natural extension toward indexing the user's own document collection, things like research papers, course notes, personal email, instead of a fixed corpus. The architecture supports this directly. Replace the corpus list in build_index.py with a directory walk, and everything downstream works unchanged.
