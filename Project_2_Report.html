GutenSearch

A Mini Search Engine over Classic Literature

Paul Semaan   Search Engine Technology   Professor Xin Qin   Spring 2026

Abstract

Abstract. GutenSearch is a small search engine I built over ten classic novels from Project Gutenberg. It puts all the search ideas from this class into one working program. That includes breaking text into words, building an inverted index, handling Boolean searches, phrase searches, and wildcard searches, ranking results two different ways with tf-idf and BM25, and fixing spelling mistakes. A Python script turns the books into one big index file. A web page then loads that file and does all the searching right in the browser, with no server. The corpus has about 778,000 words and 22,794 different terms. The index file is 5.9 MB and most searches finish in under 15 milliseconds.

1. Introduction

Everything we learned this semester came one piece at a time. Tokenization one week, inverted indexes another, tf-idf after that, then BM25, k-grams, and spelling correction. Each one made sense on its own, but you do not really get how they connect until you build something that uses all of them at once. That is what this project is. I wanted something I could actually type a search into, not just a pile of separate algorithms.

I picked ten famous novels from Project Gutenberg as the books to search. They are free to use, they are long enough that ranking actually matters, and they are well known enough that you can tell if the results make sense just by knowing the books. If you search vampire blood transylvania, Dracula should come up first. If you search for the exact phrase mr darcy, only one book should match.

The point of the project is that it is a full search engine, start to finish, from raw book files all the way to ranked results. It does not lean on any outside libraries. The build script only uses what comes with Python. The search runs in any browser. The whole thing is live at paulsemaan007.github.io/gutensearch.

2. Related Work

The methods I used are all standard. The main book they come from is Introduction to Information Retrieval by Manning, Raghavan, and Schütze [1]. The tf-idf scoring, the cosine ranking, the positional index, the k-gram index for wildcards, and the spelling correction all come straight out of that book.

The BM25 ranking comes from a paper by Robertson and Zaragoza [2]. I used their normal settings, k1 around 1.5 and b around 0.75. BM25 is different from tf-idf in two ways. It does not let one very common word take over the score, and it adjusts for how long a book is. The length part matters here because the books are very different sizes. Alice in Wonderland is about 27,000 words and Dracula is about 163,000, so one is roughly six times the other.

For comparison, Apache Lucene [3] is the big open source search engine that powers Elasticsearch and Solr. It works the same general way as GutenSearch, just much bigger, and with smarter ways of compressing the index. You can think of GutenSearch as a tiny version of one piece of Lucene, running in the browser on a small set of books.

The spelling correction is based on the idea from Kernighan, Church, and Gale [4], but simpler. Instead of a full probability model, I just rank the suggestions by how few edits it takes to get from the typo to a real word, and break ties by how common the word is. The trick of using shared 3-grams to find candidate words quickly comes from Angell, Freund, and Willett [5].

3.2 System Architecture

The system has two parts. The first part is a Python script, build_index.py, that downloads the books, breaks them into words, builds the indexes, and saves it all as one JSON file. The second part is a web page, made of index.html, style.css, and app.js, that loads that JSON file and does all the searching in the browser. Figure 1 shows how it flows.

Figure 1. How GutenSearch works. The build runs once, the search runs in the browser, and there is no server.

The good thing about doing it this way is that it is really easy to put online. You push it to GitHub, turn on GitHub Pages, and you get a live link with no setup. The downside is that the whole index has to load into memory before the first search. For ten books that takes well under a second on a normal laptop.

3.3 Tokenization and Indexing

Breaking text into words is kept simple. The script grabs runs of letters and apostrophes, makes everything lowercase, and drops the apostrophes, so can't becomes cant and O'Brien becomes obrien. I chose not to use a stemmer. A real one like Porter is a lot of extra code for a small gain on a corpus this size, and a sloppy one would just give weird results. The trade-off is that searching run will not match running. To make up for that, users can use a wildcard like runn* instead.

Common words like the and of are noted but kept in the index. They have to stay, or phrase searches break. A phrase like of the dead would not work if those words were thrown out. The ranking math already gives common words a low weight, so there is no need to remove them.

The index keeps, for every word, a list of which books it shows up in and where in each book. To keep the JSON file small, the positions are stored as gaps instead of full numbers. The first position is the real number, and after that each one is just how far it is from the one before. That makes the position data about 40 percent smaller. One entry looks like this.

term darcy df 1 postings document 1342, at word positions 147, 312, 88, 203, and so on

The 3-gram index is what makes wildcard searches work. Every word is padded with a dollar sign at each end, and then every group of three letters in that padded word points back to the word. When you run a wildcard search, the system takes the parts of the pattern with no asterisk, finds the words that contain all of those 3-grams, and then checks each one against the real pattern to throw out the wrong matches.

3.4 Query Evaluation

There are four kinds of search, and the system figures out which one you want from what you type. Quotes mean a phrase search. An asterisk means a wildcard search. The words AND, OR, or NOT mean a Boolean search. Anything else is a normal ranked search.

Boolean searches get parsed with a shunting-yard parser that turns the query into reverse Polish notation. AND and OR work on two things at a time. NOT plus a word gets merged into one negated token early on, which keeps the parser simple. Then the system walks through the parsed query and does set intersection for AND, set union for OR, and set difference for NOT.

Phrase searches grab the position lists for every word in the phrase and find the books that have all of them. Then they check the positions. For each spot the first word appears, the system checks whether the next word is right after it, and so on down the phrase. As soon as one full match is found in a book, it stops looking.

Ranked searches use either tf-idf cosine or BM25. You pick which one with a dropdown. Both return the top results, ten by default, and you can change that number. The formulas are below.

tf-idf cosine, lnc.ltc weighting
score(q, d) = sum over t in q of (1 + log tf_qt) × log(N / df_t) × (1 + log tf_dt), divided by the query norm times the document norm
BM25, with k1 = 1.5 and b = 0.75
score(q, d) = sum over t in q of idf(t) × (k1 + 1) tf_dt, divided by (tf_dt + k1 (1 − b + b × |d| / avgdl))

The idf part of BM25 is worked out with the formula log of ((N − df + 0.5) over (df + 0.5), plus 1). The document weights for tf-idf are figured out ahead of time during the build, so the only work left at search time is looking up terms, multiplying, and adding.

3.5 Spelling Correction

If a ranked search finds nothing, the system tries to fix the first real word in the query. It looks at the 3-grams of the misspelled word, finds words in the index that share enough of those 3-grams, and ranks those by how few edits it takes to get from the typo to the real word. If there is a tie, the more common word wins. The best guess shows up as a suggestion you can click to search again.

4.4 Wildcards and Spelling Correction

The wildcard search monst* matches monster, monsters, monstrous, and monstrosity, and finds three books, Frankenstein, Dracula, and The Picture of Dorian Gray. The search *ation matches over 200 words, which shows a weak spot. Very broad wildcards match too many words to show in a useful way. A better system would either cut the list off or rank the matches.

Spelling correction works well on normal typos. The word frankinstien gets fixed to frankenstein, elisabeth to elizabeth, and scroge to scrooge. It stops working when the typo is more than three edits away from any real word, or when it does not share enough 3-grams with anything in the index.

4.5 Limitations

There are a few things the system does not do well, and it is worth being upfront about them.

  • No stemming. Searching run will not match running. Wildcards are the workaround.
  • Phrase results are not ranked. A phrase search just gives back the matching books in no particular order.
  • The whole index loads at once. That is fine for ten books, but a much bigger collection would need it split up and loaded in pieces.
  • Spelling correction only kicks in when a search finds nothing. A better version would also suggest fixes when a search finds very few results.
  • The snippets are basic. They show the first place the word appears in a book, not the best place.
  • No proximity or field searches. You cannot search for words near each other, or search only the title or only the author.

5. Conclusion and Future Work

GutenSearch shows that the standard search engine methods from this class are enough to build a real, working search engine, start to finish, with no outside libraries. The whole thing is a few hundred lines of Python and a few hundred lines of JavaScript. Putting it online is just a matter of pushing it to GitHub Pages.

If I kept working on this, here is what I would do, roughly in order of how much it would help. First, add a stemmer so run matches running without needing a wildcard. Second, add query expansion with synonyms, so a search still works when the user and the author use different words for the same thing. Third, split the index into parts and load them as needed, so it could handle a lot more books. Fourth, use real relevance ratings to train the ranking, so it could do better than tf-idf or BM25 on their own. Fifth, replace the spelling correction with a proper model trained on real typos instead of the simple version it uses now.

It would also be easy to point this at your own files instead of a fixed set of books, like research papers, class notes, or email. The design already allows for it. You would just change build_index.py to read a folder instead of a list of books, and everything else would still work.
